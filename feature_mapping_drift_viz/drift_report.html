3. Drift Detection Metrics and Methods

3.1 Metric Taxonomy

Five drift types are tracked, ordered by severity. Critical issues trigger an immediate BLOCK and raise a RuntimeError before any training step proceeds.

M1 Schema Integrity BLOCK on any failure

Checks that the set of top-level keys in feature_mapping.json is identical between snapshots. Any addition or removal is immediately fatal — the downstream model cannot safely process a mapping with an unexpected schema.

added_keys   = set(curr.keys()) - set(prev.keys())
removed_keys = set(prev.keys()) - set(curr.keys())
ConditionAlertInterpretation
added_keys non-emptyBLOCKNew feature introduced — model may not handle it

Key sets equalOKSchema stable
Baseline: Zero schema drift across all 23 snapshots (May 1–26). All snapshots share exactly 40 top-level keys.
M2 Vocabulary Size Delta WARN or BLOCK

Measures how many new entries were added to each large-vocab key since the previous snapshot. An abnormally large delta can indicate a data pipeline anomaly (e.g. a bulk re-ingestion, schema change upstream, or a backfill). A negative delta (vocab shrinkage) is always a BLOCK since entries are never removed in normal operation.

M3 OOV Promotion Rate WARN or BLOCK

Counts entries that transitioned from OOV (sentinel index 5) to a unique active index. This happens when a store/game/project/audience ID accumulates enough observations to cross the count threshold. Promotions are irreversible — once active, an entry keeps its index permanently. An abnormally high promotion rate suggests a data volume spike or threshold change.

promoted_count(key) = |{e ∈ shared(prev, curr) : prev[key][e] == 5 AND curr[key][e] > 5}|

M4 Active Index Regression BLOCK — always zero tolerance

Detects any previously-active entry (index > 5) whose index value changed between snapshots. This is a hard corruption signal: embedding tables are indexed by these integers, so any reassignment breaks alignment between the old model weights and the new mapping, causing silent embedding lookups to the wrong row.

regressions(key) = {e: (prev_idx, curr_idx)
                    for e in shared(prev, curr)
                    if prev_idx > 5 AND curr_idx != prev_idx}
ConditionAlertInterpretation
regressions non-emptyBLOCKEmbedding alignment broken — do not train or deploy
regressions emptyOKAll active indices stable
Baseline: Zero active-index regressions observed across all 22 single-day transitions in the window. OOV→active promotions (M3) are expected and do not count as regressions.
M5 OOV Rate Delta WARN or BLOCK

Tracks the fraction of entries sitting at the OOV sentinel (5). This fraction should decline very slowly as the mapping accumulates more observations and promotes entries. A sudden increase suggests a data regression or threshold raise; a sudden decrease suggests mass promotion or a threshold drop.

oov_rate(key)       = count(v == 5 for v in curr[key].values()) / len(curr[key])
oov_rate_delta(key) = oov_rate(curr) - oov_rate(prev)
ConditionAlertInterpretation
delta > +1.0%BLOCKLikely data regression — large influx of unseen IDs
delta > +0.5%WARNUnusual OOV volume or threshold raised
delta < −1.0%WARNMass promotion event — possible threshold lowered
−1.0% ≤ delta ≤ +0.5%OKNormal slow decline
Baseline: store_id OOV rate declined from 75.8% → 75.4% over 26 days (~0.05% per week). Expected: very slow decrease as the mapping matures.
M6 Count Threshold Stability WARN

Verifies that the minimum observation count among all active entries matches the configured threshold in datagen_config.track_feature_counts. If an active entry has a count below the threshold, the threshold was silently lowered — which would admit more low-frequency IDs into the embedding table than expected.

3.9 Composite Drift Score (WDS)

A single scalar summarising all non-critical signals. Regression count has a hard penalty (weight = 100) to ensure any active-index corruption dominates the score regardless of other metrics.

WDS = 0.3 * normalized_vocab_delta
    + 0.3 * normalized_promotion_rate
    + 0.3 * abs(oov_rate_delta) * 100
    + 100 * regression_count

where:
  normalized_vocab_delta    = Σ max(0, vocab_delta(k) - expected(k)) / block_threshold(k)
  normalized_promotion_rate = Σ max(0, promotions(k)  - expected(k)) / block_threshold(k)
WDS rangeStatusAction
0.0 – 0.3NormalNo action required
0.3 – 0.7ElevatedInvestigate root cause; do not block training
0.7 – 1.0HighRequire manual sign-off before training proceeds
> 1.0 or regression_count > 0CriticalBLOCK — do not train or deploy

3.10 Multi-Day Gap Handling

When the previous snapshot is more than 1 day old, M2 and M3 thresholds are scaled linearly by elapsed_days:

scaled_warn  = single_day_warn  * elapsed_days
scaled_block = single_day_block * elapsed_days

Example: the May 01→05 4-day gap produced +3,167 store_id additions and 1,285 promotions. With 4× scaling, the effective block threshold becomes 7,200 and 2,400 respectively — both comfortably exceeded the observed values, correctly returning OK.

5. Key Findings Summary

  1. Schema is fully stable: All 23 snapshots share exactly 40 top-level keys. Zero schema drift over 26 days.
  2. Monotonic growth, no deletions: Large-vocab mappings only ever gain entries. Removals are anomalous and trigger a hard BLOCK.
  3. Some enum keys grow slowly: os_version, platform_os_version, device_atlas_device_vendor, device_atlas_gpu, and geolocation_country added new entries. All additive — no index reassignments. Treat as normal, not an alert.
  4. OOV thresholds are per-key: store_id = 3,000 · others = 500. developer_id, device_type, and apptopia_cross_store_app_id are effectively ungated (near-zero OOV entries).
  5. Active indices never reassign: Zero active-index regressions across all 22 single-day transitions. Any regression = immediate BLOCK.
  6. No anomalous spikes: All single-day transitions fall within expected ranges. The May 01→05 gap produced proportionally scaled deltas.
  7. Healthy OOV rate: 75.4–75.8% of store_id entries are OOV, slowly declining at ~0.1% per two weeks.
